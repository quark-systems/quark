How quarkd works

quarkd is Quark's local control plane: one Rust daemon on 127.0.0.1:7380 that keeps the state, runs the background loops, and starts the processes the agents live in. It drives almost every outside tool as a command-line program rather than a library.

1 · The processes it runs

The desktop app and QuarkBar only talk HTTP to quarkd. quarkd starts the PTY host (quark-ptyd) and a tmux server; workers and coordinators run inside those, so they keep running when quarkd restarts. Agents report back over quarkd's own HTTP API.

quarkd itself

A loopback daemon with one home

  • Won't listen on anything but loopback; default 127.0.0.1:7380 (QUARKD_LISTEN).
  • Serves the /v1 REST API, the /v1/events WebSocket, the worker protocol under /v1/worker, and an MCP server plus turn-end hooks for coordinators.
  • State lives in ~/.quark: quark.db (store), events.db (append-only event log, replayed on start), daily JSONL logs.
  • QuarkBar registers it as a LaunchAgent on macOS; on Windows it runs in WSL on the same port.

tokio tasks in serve()

Background loops

  • Supervisor tick 2s · dispatch tick 5s · projector 5s
  • PR center reads the forge every 30s
  • Accounts read quota every 300s
  • Housekeeping, coordinator recovery, coordinator switch, usage ingest, triggers, fleet check, Beads watch

restart behaviour

Why agents outlive quarkd

  • quark-ptyd is the same binary run as quarkd ptyd (or QUARK_PTYD), and it holds the PTY sessions.
  • On restart the supervisor replays the event log, takes back current sessions and kills any no generation owns.
  • Dispatch checks with the host before spawning again, so a task never starts twice.

2 · The tools it shells out to

Apart from the agents, quarkd's outside dependencies are command-line programs it finds on PATH and runs with Command::new. Dashed ones only run when configured. Blue ones go over the network.

what each tool is for

Where they're called from

  • git: the native worktree pool (a Rust port of treehouse 3.1.2 working on treehouse's own pool state), rebasing and re-verifying before a merge, Project repo setup.
  • gh: GhForge uses whatever account gh is signed in to, for PRs, checks, merges and repo lists. Verify also pushes rebased heads through it.
  • bd / dolt: one Beads database per Project, set up on its own and watched. Coordinators reach it through bd with BEADS_DIR.
  • quota-axi: account quota snapshots. quota-axi doesn't cover Bob or Kiro, so quarkd reads those itself: kiro-cli chat --v2 --no-interactive /usage, and Bob's admin API through curl (key on stdin) or ~/.bob/db/bob.db.
  • security: account API keys and the classifier key live in the login Keychain, written through security -i on stdin.

not drawn

Smaller and one-off spawns

  • Agent CLIs from 15 harness manifests (claude-code, codex, kiro, bob, pi, gemini, opencode, cursor-agent, …), which ptyd runs. quarkd itself only runs their -V and model-list probes.
  • Repo gate commands through bash, and trigger commands from channels.
  • Host probes: sysctl, df, ps, hostname.
  • Subcommands that run without the daemon: doctor, diagnose, triage (files bugs with bd), quota bob|kiro, openapi, import firstmate.
